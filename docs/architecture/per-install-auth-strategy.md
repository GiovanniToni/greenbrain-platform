# Per-Install Auth Strategy
> Authentication model for the GreenBrain owner dev-cloud instance and all
> customer-local installations.
> Based on decision: `docs/architecture/brand-access-and-tenant-routing-decision.md`.
> Updated: 2026-04-02.

---

## Decision

Authentication in GreenBrain V1 is **per-installation**.

Each installation — the owner's dev-cloud and every customer's local install —
has its own independent user database, its own JWT secret, and its own session
space. Sessions are not shared, portable, or federated between installations.

This is the only auth model consistent with the installation-isolated product
architecture.

---

## 1. Current Reality

Auth is currently provided by Supabase JS in the browser:
- `src/integrations/supabase/client.ts` — Supabase SDK client
- `src/hooks/useAuth.tsx` — reads from Supabase session
- `src/hooks/useGardenCenterSettings.ts` — queries Supabase PostgREST directly
- `src/pages/Login.tsx` — posts to Supabase auth endpoint

This works for the dev-cloud mode where `VITE_SUPABASE_URL` is available.
It is **completely incompatible** with client-local: customer installs have no
Supabase account and no Supabase URL.

Supabase auth must be replaced before any customer installation is functional.

---

## 2. Target Auth Model

### FastAPI JWT — same binary, both modes

The FastAPI backend provides auth for both modes. No Supabase dependency.
No external auth service required at runtime.

```
Browser → POST /api/v1/auth/login  →  FastAPI validates credentials
                                        against local users table
                                   →  Returns JWT signed with JWT_SECRET
Browser → GET  /api/v1/auth/me     →  FastAPI validates JWT
                                   →  Returns user profile
Browser → GET  /api/v1/analytics/* →  FastAPI checks JWT in Authorization header
```

The same FastAPI binary and the same auth endpoints work identically on:
- `app.greenbrain.it` (owner dev-cloud)
- `<slug>.greenbrain.it` → customer server (via tunnel)
- `http://localhost` on customer server (local access)

### Why auth must remain per-installation

1. **Data isolation** — each customer's user table lives in their own PostgreSQL.
   A user from installation A must never be able to authenticate against
   installation B.

2. **JWT secret isolation** — JWT tokens are signed with a secret unique to each
   installation. A token issued by installation A is cryptographically invalid
   at installation B.

3. **No central identity** — there is no central GreenBrain identity server. The
   owner does not hold master credentials for customer installations.

4. **Offline operation** — customer installations must function without internet
   access. A central auth server would break offline operation.

5. **Privacy** — customer user identities (email addresses, names) remain on the
   customer's server. The owner never has access to this data.

## 3. JWT Secret Strategy

| Installation | Secret location | Value | Generation |
|---|---|---|---|
| Owner dev-cloud | `infra/env/dev.env` as `JWT_SECRET` | Minimum 32 random bytes (hex or base64) | Generated once by owner; never committed |
| Customer install | `infra/env/client.env` as `JWT_SECRET` | Minimum 32 random bytes | Generated by `install.sh` on first install |

**Generation command:**
```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
# or
openssl rand -hex 32
```

**`install.sh` must auto-generate `JWT_SECRET`:**
```bash
JWT_SECRET=$(openssl rand -hex 32)
sed -i "s/^JWT_SECRET=.*/JWT_SECRET=$JWT_SECRET/" infra/env/client.env
```

The secret must:
- Never be committed to source control
- Be present in `.gitignore` as part of `infra/env/client.env`
- Be backed up by the customer as part of their backup procedure (loss of
  JWT_SECRET invalidates all existing sessions — users must log in again)
- Be unique: two installations must never share a secret

## 4. User Table

A minimal `users` table in public schema is required. This does not exist in
the current init files and must be added as part of the auth implementation.

**Recommended schema:**
```sql
CREATE TABLE IF NOT EXISTS public.greenbrain_users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email           TEXT UNIQUE NOT NULL,
    hashed_password TEXT NOT NULL,
    full_name       TEXT,
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    is_admin        BOOLEAN NOT NULL DEFAULT FALSE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_login_at   TIMESTAMPTZ
);
```

This table is local to each installation. The owner's dev-cloud has its own
`greenbrain_users`. Each customer has their own `greenbrain_users`. They are
completely independent.

Add to an init wave file: `client-runtime/sql/init/14_schema_auth.sql`
(or incorporate into Wave 7B.4 if auth and ETL are delivered together).

## 5. Password Storage

Use `passlib` with `bcrypt` hashing. No plaintext passwords. No MD5. No SHA-1.

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(password: str) -> str:
    return pwd_context.hash(password)

def verify_password(plain: str, hashed: str) -> bool:
    return pwd_context.verify(plain, hashed)
```

`bcrypt` work factor: default (12). Sufficient for V1.

## 6. FastAPI Endpoints Required

All endpoints live in `apps/backend/app/api/v1/auth.py`.

| Endpoint | Method | Auth required | Description |
|----------|--------|--------------|-------------|
| `/api/v1/auth/login` | POST | No | Validates credentials; returns JWT access token |
| `/api/v1/auth/me` | GET | Yes (JWT) | Returns current user profile |
| `/api/v1/auth/setup` | POST | No (once only) | Creates first admin user; disabled after first user exists |
| `/api/v1/settings/garden-center` | GET | Yes (JWT) | Returns garden center settings (replaces Supabase PostgREST call) |

### `/api/v1/auth/login` — request/response

```
POST /api/v1/auth/login
Content-Type: application/json
{"email": "admin@example.com", "password": "..."}

→ 200 {"access_token": "<jwt>", "token_type": "bearer", "expires_in": 3600}
→ 401 {"detail": "Invalid credentials"}
```

### `/api/v1/auth/me` — response

```
GET /api/v1/auth/me
Authorization: Bearer <jwt>

→ 200 {"id": "...", "email": "...", "full_name": "...", "is_admin": true}
→ 401 {"detail": "Not authenticated"}
```

### `/api/v1/auth/setup` — first-run only

```
POST /api/v1/auth/setup
Content-Type: application/json
{"email": "admin@...", "password": "...", "full_name": "Admin"}

→ 201 {"id": "...", "email": "..."} — only if no users exist yet
→ 409 {"detail": "Setup already completed"} — if any user already exists
```

This endpoint must check `SELECT COUNT(*) FROM greenbrain_users` before creating.
It is self-disabling: once one user exists, it always returns 409. No flag needed.

## 7. JWT Implementation

```python
# apps/backend/app/core/security.py

from datetime import datetime, timedelta
from jose import JWTError, jwt
from app.core.config import settings

ALGORITHM = "HS256"

def create_access_token(subject: str) -> str:
    expire = datetime.utcnow() + timedelta(minutes=settings.JWT_EXPIRE_MINUTES)
    return jwt.encode(
        {"sub": subject, "exp": expire},
        settings.JWT_SECRET,
        algorithm=ALGORITHM
    )

def decode_token(token: str) -> str:
    """Returns the subject (user email or id) or raises JWTError."""
    payload = jwt.decode(token, settings.JWT_SECRET, algorithms=[ALGORITHM])
    return payload["sub"]
```

Required config additions in `apps/backend/app/core/config.py`:
```python
JWT_SECRET: str        # from env; must be present or app fails to start
JWT_EXPIRE_MINUTES: int = 60  # default 1 hour; configurable
```

FastAPI dependency for protected routes:
```python
from fastapi import Depends, HTTPException, status
from fastapi.security import HTTPBearer, HTTPAuthorizationCredentials

bearer = HTTPBearer()

def get_current_user(credentials: HTTPAuthorizationCredentials = Depends(bearer)):
    try:
        subject = decode_token(credentials.credentials)
    except JWTError:
        raise HTTPException(status_code=401, detail="Not authenticated")
    # fetch user from DB; return user object
    ...
```

All analytics, dashboard, planner, and ops endpoints must use this dependency.

## 8. Frontend Auth Adaptation

Replace Supabase JS auth with calls to the FastAPI JWT endpoints.

### Files to change

| File | Change |
|------|--------|
| `src/hooks/useAuth.tsx` | Remove Supabase session; store JWT in `localStorage` or memory; expose `login()`, `logout()`, `user`, `isAuthenticated` |
| `src/hooks/useGardenCenterSettings.ts` | Replace `supabase.from('garden_center_settings')` with `apiClient.get('/api/v1/settings/garden-center')` |
| `src/pages/Login.tsx` | Call `POST /api/v1/auth/login`; store token; redirect to dashboard |
| `src/components/layout/TopBar.tsx` | Call `logout()` from new `useAuth`; clear stored token |
| `src/integrations/supabase/client.ts` | **Delete** after all callers replaced |
| `apps/frontend/package.json` | Remove `@supabase/supabase-js` |

### Token storage recommendation

Store the JWT in `localStorage` under key `gb_access_token`. This persists across
page refreshes without a backend session store. Alternative: `sessionStorage` for
more conservative security (token lost on tab close).

Do not store JWTs in cookies for V1 (requires CSRF protection; adds complexity).

### `apiClient.ts` auth header

All authenticated requests must include:
```typescript
headers: {
  "Authorization": `Bearer ${localStorage.getItem("gb_access_token")}`
}
```

This is typically injected via an Axios interceptor or a wrapper function.

### Removal sequence (must be in order)

1. Backend: implement all 4 endpoints (§6) and confirm with curl
2. Frontend: replace `useAuth.tsx` first; test login
3. Frontend: replace `useGardenCenterSettings.ts`
4. Frontend: update `Login.tsx` and `TopBar.tsx`
5. Frontend: delete `src/integrations/supabase/client.ts`
6. Frontend: `npm uninstall @supabase/supabase-js`
7. Frontend: `npm run build` — must succeed with zero Supabase imports

## 9. Interaction with Customer Remote Access

When a customer accesses `<slug>.greenbrain.it`, the auth flow is identical
to local access. The tunnel is transparent to the application layer.

```
Browser at <slug>.greenbrain.it
  → POST /api/v1/auth/login  → Cloudflare Tunnel → Customer nginx → Customer FastAPI
  ← JWT signed with customer's JWT_SECRET

Subsequent requests:
  → GET /api/v1/analytics/series  with JWT  → Customer FastAPI → Customer PostgreSQL
  ← Customer analytics data
```

The JWT issued by a customer's installation is only valid for that installation.
It cannot be used at `app.greenbrain.it` or any other customer's subdomain.

CORS must be configured on the customer's backend to allow both the local
origin and the subdomain origin:
```python
allow_origins=[
    "https://<slug>.greenbrain.it",
    "http://localhost",
    "http://localhost:80",
]
```

## 10. What Must NOT Be Done in V1

| Item | Why not |
|------|---------|
| Central auth server / SSO | Breaks offline operation; contradicts per-install isolation |
| OAuth / OIDC | Unnecessary complexity; external dependency; V1.1+ |
| Shared JWT secret across installations | Violates isolation; token from one install valid at all others |
| Password reset via email | Requires SMTP; external dependency; V1.1 |
| Multi-factor authentication | V1.1 |
| User roles beyond admin/non-admin | Complexity not justified for single garden-center V1 |
| Storing JWTs in httpOnly cookies | Requires CSRF protection; adds backend complexity; V1.1 |
| Token refresh endpoint | V1 uses short-lived tokens (1 hour); user re-logs in; V1.1 |
| Admin panel for user management | Not required for V1; one admin per install is sufficient |
| Owner access to customer user table | Never; would violate data ownership principle |

## 11. First Admin Creation Flow

When `install.sh` runs on a fresh installation:

```
1. install.sh generates JWT_SECRET and writes to infra/env/client.env
2. Docker stack starts; database initialized with init waves
3. install.sh generates a temporary admin password:
      ADMIN_PASS=$(openssl rand -base64 12)
4. install.sh calls:
      curl -X POST http://localhost:8002/api/v1/auth/setup         -d '{"email":"admin@greenbrain.local","password":"$ADMIN_PASS","full_name":"Admin"}'
5. install.sh prints to screen (never to a file):
      ╔══════════════════════════════════════╗
      ║ GreenBrain installation complete     ║
      ║ URL:      http://localhost           ║
      ║ Email:    admin@greenbrain.local     ║
      ║ Password: <ADMIN_PASS>              ║
      ║ Change your password after login!   ║
      ╚══════════════════════════════════════╝
6. ADMIN_PASS is never stored; only printed once
```

The customer must change the admin password immediately after first login.
A "change password" endpoint (`PUT /api/v1/auth/password`) is the minimum
post-V1 addition required.

## 12. Analytics, Dashboard, and Planner — Auth Dependency

All product domain endpoints are protected by JWT auth:
- Analytics (`/api/v1/analytics/*`) — requires valid JWT
- Dashboard (`/api/v1/dashboard/*`) — requires valid JWT
- Planner (`/api/v1/planner/*`) — requires valid JWT
- Ops (`/api/v1/ops/*`) — requires valid JWT (or at minimum `/ops/health` is public)
- Forecast (`/api/v1/forecast/*`) — requires valid JWT

The analytics domain is the core product domain. Its data is only served to
authenticated users. No public analytics endpoint exists. No API key alternative
in V1.

`/health` and `/health/db` remain public (no JWT required) — these are
infrastructure probes, not business data endpoints.
